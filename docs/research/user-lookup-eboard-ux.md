# E-Board User Lookup: showing one Member's standing

Researched 2026-09-27 against the current `/eboard/user-lookup` page (`frontend/src/pages/eboard/UserPointsLookup.tsx`) and the new point model (`lib/computeStanding.ts`, `lib/requestReview.ts`, `CONTEXT.md`).

## The question

An E-Board reviewer searches for one Member and opens their record. Today the page shows four stored-counter cards (Total, Fall, Spring, Voter Eligible) and a per-category VE/NVE table built from `fallPoints`, `springPoints` and `{category}PointsVE/NVE`. Under the new model those numbers mean nothing: points are computed from Attendance (a redeemed code, an approved Point Request, or E-Board entry) plus Adjustments. A General Member needs 15 VE Points (8 for MLP Spring). A Cabinet Member also has 20 Cabinet Points toward Graduating Cabinet, Core Events (Missed Events, Strikes, Make-ups) and Semester Requirements. E-Board also wants the Member's Point Requests with status, reviewer and notes, so they can see where each point came from. What should the page show, in what order, and how?

## Findings

### 1. Summary first, ledger second

- **Progressive disclosure.** "Initially, show users only a few of the most important options", with the rest on request, and a control labelled so it "sets clear expectations" ([Nielsen 2006](https://www.nngroup.com/articles/progressive-disclosure/)). The reviewer's frequent question is "is this Member on track / eligible?". The full list of where every point came from is the less frequent, drill-down question.
- **Record pages lead with a short strip of key facts.** Salesforce's compact layout "control[s] which fields your users see in the highlights panel at the top of a record", up to seven in Lightning, with the first in an accented font ([Salesforce Help: Compact Layouts](https://help.salesforce.com/s/articleView?language=en_US&id=platform.compact_layout_overview.htm&type=5); [Trailhead: Customize Record Highlights](https://trailhead.salesforce.com/content/learn/modules/lex_customization/lex_customization_compact_layouts)). Related records (lists, activity) sit below or in tabs.
- **Staff "context" views are deliberately small.** Canvas's student context card is "a simplified overview of a student's progress": current grade, missing and late assignments, activity, plus links out to the full grades and analytics pages ([Canvas Instructor Guide: context card](https://community.instructure.com/en/kb/articles/660965-how-do-i-view-a-context-card-for-a-student-in-a-course)). Note what it leads with: the grade and the *exceptions* (missing, late), not the full list of assignments.
- **Stripe's customer page splits the same way.** Basic details and a spending summary on one side, "an overview of the customer's recent activity" in the main area, and "a more detailed history" in a separate events and logs tab ([Stripe Support: customer information](https://support.stripe.com/questions/manage-a-customer-s-information-and-payments)).
- **Glanceable means answer-first.** Dashboards should let users "glance ... and immediately see answers" ([Laubheimer 2017](https://www.nngroup.com/articles/dashboards-preattentive/)). For HSA the answer is a verdict per goal ("Voter eligible: yes/no", "Graduating Cabinet: 14 of 20"), not a grid of numbers the reviewer has to interpret.

### 2. Provenance: where each point came from

- **A ledger is the source; the balance is derived from it.** Event sourcing keeps every change, so current state can be rebuilt "by re-running the events", and the log doubles as an audit trail ([Fowler: Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)). This is exactly HSA's new model (ADR 0002: Attendance ledger calculated on read). A reviewer who can see the entries can check the total themselves.
- **Stripe types every ledger entry and links its source.** Each balance transaction has a `type` (charge, refund, adjustment...) and a `source` field with "the ID of the related Stripe object"; adjustments are entries "made outside of the normal charge/refund flow" whose `description` "describes the purpose" ([Stripe: Balance transaction types](https://docs.stripe.com/reports/balance-transaction-types)). The HSA equivalents are Attendance by code / by Point Request / by E-Board entry, and Adjustment with its note.
- **What each entry needs.** OWASP lists the audit attributes as when, where, who and what (type, description) ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). The government timeline components ask the same of each item: a short title, the date, "the author or source", an optional short description and at most one link ([MOJ Timeline](https://design-patterns.service.justice.gov.uk/components/timeline/)). The byline is useful "if your timeline includes both agent actions and automated events" ([DWP Timeline: how it works](https://design-system.dwp.gov.uk/components/timeline/how-it-works)), which is HSA's mix: self-service code check-ins and E-Board approvals and Adjustments.
- **Keep entries simple; details go elsewhere.** DWP: "Do not use the description to contain full details of an event", and allow no interactive element except a single text link ([DWP Timeline: how it works](https://design-system.dwp.gov.uk/components/timeline/how-it-works)). The timeline is "a record of events in time order", not "a working environment" or a task list ([DWP Timeline](https://design-system.dwp.gov.uk/components/timeline); [MOJ Timeline](https://design-patterns.service.justice.gov.uk/components/timeline/)). So the review action belongs in Point Request Review, linked from the entry.
- **Order.** "Most recent events first, unless user research suggests a different order is better" ([MOJ Timeline](https://design-patterns.service.justice.gov.uk/components/timeline/)).
- **One timeline vs tabs.** Timelines exist to show "updates from different people or systems in one place" ([MOJ Timeline](https://design-patterns.service.justice.gov.uk/components/timeline/)). Tabs suit content users "don't need to simultaneously see"; otherwise they "must repeatedly switch between tabs to compare" ([Sunwall 2024](https://www.nngroup.com/articles/tabs-used-right/)). A reviewer reconciling "why is it 12?" needs check-ins, approved requests and Adjustments side by side, which argues for one points ledger, not three tabs. Stripe does use a separate tab, but only for the raw event log, a lower-level view than the activity overview ([Stripe Support](https://support.stripe.com/questions/manage-a-customer-s-information-and-payments)).

### 3. Point Request history

- **Status in words, few statuses, consistent colour.** GOV.UK tags show status, use adjectives, must not rely on "colour alone", keep the same colour everywhere the tag appears, and should "start with the smallest number of statuses" ([GOV.UK Tag](https://design-system.service.gov.uk/components/tag/)). Atlassian's lozenge says the same: "Combine color with a logical and concise label", use subtle lozenges in content-heavy layouts like tables, and "approved" is its example of a success status ([Atlassian: Lozenge](https://atlassian.design/components/lozenge/lozenge/usage)). HSA already has exactly three: Pending, Approved, Denied.
- **Tags are not links.** Users "would see no visual difference between interactive and non-interactive tags" ([GOV.UK Tag](https://design-system.service.gov.uk/components/tag/)). "Review" must be a separate link or button.
- **Show the latest state, then history, with dates and plain-language reasons.** NN/g's status-tracker guidelines: prioritise "the latest update", write in "plain language", show previous updates with dates, and communicate next steps ([NN/g: Status trackers](https://www.nngroup.com/articles/status-tracker-progress-update/)). For a denied request that means the deny reason and reviewer; for a pending one, how long it has waited.
- **Filtering.** If a list is filtered, filters must be "discoverable, quick" with "a clear visual indication that filters are active" ([NN/g: Data tables](https://www.nngroup.com/articles/data-tables/)). A single Member rarely has more than a few dozen requests, so a Pending-first sort with Pending/Approved/Denied chips is enough; no search needed (inference).
- **Pending and denied are not points.** Only approved Attendance counts (CONTEXT.md, Make-up). Showing a pending request inside the points ledger without a clear status would let the reviewer double-count; Stripe likewise marks balances `pending` vs `available` rather than merging them ([Stripe: Balance transaction types](https://docs.stripe.com/reports/balance-transaction-types)).

### 4. Goal progress and requirement checklists

- **Length on a common scale is read most accurately**, colour is not seen as ordered ([Laubheimer 2017](https://www.nngroup.com/articles/dashboards-preattentive/)); a single bar toward 15 (or 20) is the most accurate "how far along" encoding. This repeats the General Member view research (`general-member-points-view-ux.md`), and E-Board should see the same number the Member sees.
- **Numbers as numerals.** Digits catch the eye when scanning ([Nielsen 2007](https://www.nngroup.com/articles/web-writing-show-numbers-as-numerals/)). "11 of 15 VE Points" should be printed; a bar alone is not enough and would fail WCAG 1.4.1 if it carried status by colour ([Understanding 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)).
- **Checklists: surface what needs attention.** GOV.UK's task list shows "which tasks they've completed and which still need their attention" and made "Completed" plain text so it "will draw more attention to tasks that require action" ([GOV.UK Task list](https://design-system.service.gov.uk/components/task-list/); [Complete multiple tasks](https://design-system.service.gov.uk/patterns/complete-multiple-tasks/)). For Semester Requirements that means the missing ones are tagged, the met ones are quiet. Canvas's context card does the same with "missing" and "late" ([Canvas Instructor Guide](https://community.instructure.com/en/kb/articles/660965-how-do-i-view-a-context-card-for-a-student-in-a-course)).
- **Different Member types, different blocks.** Salesforce assigns different compact layouts per record type so each shows its own key fields ([Salesforce Help: Compact Layouts](https://help.salesforce.com/s/articleView?language=en_US&id=platform.compact_layout_overview.htm&type=5)). A General Member's record should not show empty Cabinet Points or Core Events blocks; a Cabinet Member's needs them. E-Board Members are exempt from Core Events, Semester Requirements and Strikes (CONTEXT.md), so their page should say "Exempt", not "0 of 9".

### 5. Record-page layout and mobile

- **Header: who, what role, key facts.** The highlights panel pattern puts identity first, then a handful of key fields ([Trailhead: Record Highlights](https://trailhead.salesforce.com/content/learn/modules/lex_customization/lex_customization_compact_layouts)). For profile facts (email, graduation year, involvement, cabinet, position) a GOV.UK summary list fits: "key facts" as key–value pairs; not for "tabular data" ([GOV.UK Summary list](https://design-system.service.gov.uk/components/summary-list/)). GOV.UK notes the summary list/card "works well in case management systems".
- **Tabs vs single scroll.** Use tabs only for clear groupings users don't need to compare; otherwise "a single-page layout with subheadings" ([Sunwall 2024](https://www.nngroup.com/articles/tabs-used-right/)). Standing, points ledger and requests are all consulted together when judging one Member, which favours a single scroll with headings, the ledger and request history collapsible.
- **Tables on a phone.** "Only 2 columns may fit legibly on a narrow mobile screen", and a table must first work on a large screen ([NN/g: Mobile tables](https://www.nngroup.com/articles/mobile-tables/)). A ledger row of date · event · source · VE · Cabinet points is five columns; on phones it should stack into two-line list rows. Numeric columns right-aligned on desktop ([GOV.UK Table](https://design-system.service.gov.uk/components/table/)).
- **Accordions on mobile** give "the big picture before focusing on details" but shouldn't jump scroll ([Budiu 2015](https://www.nngroup.com/articles/mobile-accordions/)). A native `<details>` gives accessible disclosure behaviour for free ([WAI-ARIA APG: Disclosure](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)).

### 6. No raw stored fields, no numbers that disagree

- **One name, one number.** "Users should not have to wonder whether different words, situations, or actions mean the same thing" ([NN/g: Consistency and standards](https://www.nngroup.com/articles/consistency-and-standards/)). Today's page labels `fallPoints + springPoints` "Total Points" and shows a separately computed "Voter Eligible Points" card next to it; CONTEXT.md defines Total Points as *the same number* as VE Points. Two numbers with overlapping names that disagree is exactly what this heuristic warns against.
- **Derive, don't store twice.** With an event-sourced ledger, state is rebuilt from events ([Fowler: Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)); the page should call the same `computeStanding` the Member's Overview uses, and never read the legacy counters (`fallPoints`, `springPoints`, `{category}PointsVE/NVE`, `otherPoints`), which the cut-over (#78) retires.
- **Make the total reconcilable.** Stripe gives each balance entry a type and source so a balance can be traced back ([Stripe: Balance transaction types](https://docs.stripe.com/reports/balance-transaction-types)). If the ledger's VE column sums to the headline VE Points (Attendance plus Adjustments), the reviewer can verify it by eye.

## Recommendations for HSA User Lookup

Sourced unless marked **(inference)**.

1. **Drop every stored-counter field** from the page: the Total/Fall/Spring cards and the category VE/NVE table. Compute everything with `computeStanding` (the same function behind the Member's Overview) from Attendance plus Adjustments, so E-Board and the Member always see the same number. Use "VE Points" (or "Total Points", meaning the same thing) and "Cabinet Points" exactly; never show two different "total"s. (§6)
2. **Header**: name, email, role ("General Member", "MLP Member · Spring", "Cabinet Member · {cabinet}", "E-Board · {position}", "Web-team Tester" when relevant), graduation year. Profile facts as a summary list, not cards. (§5)
3. **Standing strip directly under the header, answering "on track?"** One row per goal with a numeral, a single-colour bar and a word verdict: "VE Points 11 of 15 · Not yet voter eligible" (8 for MLP Spring). Cabinet Members add "Cabinet Points 14 of 20 toward Graduating Cabinet", "Missed Events to make up: 2 · Strikes: 1" (with "At risk of probation" at 3+), and "Semester Requirements: 6 of 9 this Semester". E-Board Members show VE Points only and "Exempt from Core Events, Semester Requirements and Strikes". General Members get no Cabinet blocks at all. (§1, §4)
4. **Pending line in the strip**: "2 Point Requests pending (up to +4 VE Points)" linking to the request history, never added into the headline number. (§3)
5. **Cabinet detail sections below the strip**: open Missed Events first (each with its Strike tag and, for E-Board only, Excused / Unexcused, since only E-Board sees that split), then Make-ups showing which Attendance covered which Missed Event, then unmet Semester Requirements tagged, met ones as plain text inside a `<details>`. Reuse the list design from `cabinet-core-events-missed-ux.md`. (§4)
6. **One points ledger, newest first**, not separate tabs per source. Each row: date, event name and Event Type, a source tag in words ("Code check-in", "Point Request", "Entered by E-Board", "Adjustment"), VE and Cabinet points, a byline for anything E-Board touched ("Approved by {name}, {date}"; Adjustment note shown inline), and at most one link (the Point Request, or the code). Footer row: the sum, equal to the headline. Collapsed by default behind a summary like "Points ledger · 14 entries". (§2, §6)
7. **Point Request history as its own section** (it contains non-points: pending and denied), Pending first, then newest. Each row: activity name, event date, submitted date, points requested, a status tag (Pending / Approved / Denied, words plus colour, same colours as Point Request Review), reviewer and date, and the review notes or deny reason in plain text. Filter chips Pending / Approved / Denied with the active one clearly marked; hide the chips when there are fewer than ~5 requests **(inference)**. (§3)
8. **Link to the review tool, don't embed it.** A "Review" link on each Pending request to `/eboard/point-requests`. That page has no deep-link parameter today, so add one (e.g. `?request={id}`) to open that request directly **(inference: the sources say link to details elsewhere; the URL shape is ours)**. Keep approve/deny out of the lookup page. (§2, §3)
9. **Single scroll with headings, not tabs**: header → standing → (Cabinet) Missed Events / Semester Requirements → points ledger → Point Requests. The reviewer needs these together to answer one question. (§5)
10. **Mobile**: single column; the standing strip stacks one goal per line; ledger and request rows become two-line list rows (event + tags on line 1, date · source · points on line 2) instead of a 5-column table below ~600px; `<details>` for the long sections. (§5)
11. **Status never by colour alone**: every tag and verdict in words; no legend. (§3, §4)
12. **(inference)** Show a small "Includes {n} Adjustments" note next to VE Points when Adjustments exist, so a reviewer knows part of the total doesn't trace to an event. Not prescribed by a source, but follows from Stripe separating `adjustment` entries and HSA requiring a note on each.
